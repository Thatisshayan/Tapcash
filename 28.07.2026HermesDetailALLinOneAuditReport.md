### 3C. Critical Security Issues Found

#### P0 — CRITICAL ISSUE 1: Dummy API Key Fallback in `firebase.ts`

**File:** `src/lib/firebase.ts`, line 7

```ts
apiKey: proces..._KEY || 'AIzaFirebaseDummyKeyForBuild',
```

If `NEXT_PUBLIC_FIREBASE_API_KEY` is missing, the client SDK silently falls back to a dummy key and will fail to connect. Not an exploit vector per se, but it masks configuration errors. The Zod schema in `env.ts` validates this at build time, but the runtime fallback in `firebase.ts` bypasses that guard for the client-side SDK.

**Fix:** Remove the fallback, let it throw on missing configuration.

---

#### P0 — CRITICAL ISSUE 2: Production Fallback to `demo-project`

**File:** `src/lib/firebase.ts`, line 9

```ts
projectId: process.env.NEXT_PUBLIC_FIREBASE_PROJECT_ID || 'demo-project',
```

If `NEXT_PUBLIC_FIREBASE_PROJECT_ID` is missing, the app connects to the fake `demo-project` in production. This could cause silent data leaks or write failures in production if the env var is not properly set in Vercel.

**Fix:** Remove fallback, fail loud — same pattern as Issue 1.

---

#### P1 — ISSUE 3: Legacy Admin Routes Use Bearer Tokens

`ALLINREPORT.md` (line 56) identifies that legacy admin routes use Bearer tokens instead of cookie-based sessions. This bypasses session revocation. The current `/api/auth/session` route correctly issues httpOnly admin cookies with CSRF tokens, but there are legacy admin API routes that use `Authorization` header bearer tokens instead.

**Fix:** Audit all `src/app/api/admin/*` routes to confirm they all use the admin session cookie pattern from `/api/auth/session`.

---

#### P1 — ISSUE 4: Firebase Functions v1 Deprecated

`IMPLEMENTATION_COMPLETE.md`, line 39 of LAUNCH_CHECKLIST, and `ALLINREPORT.md` line 39 identify that the Functions directory uses `firebase-functions/v1`. The v1 API is deprecated. Firebase Functions v2 (or Vercel Functions) is the current standard.

**Fix:** Migrate to v2.

---

#### P2 — ISSUE 5: No Automated Secret Rotation

`SECURITY_OPS.md` (133 lines) describes the manual rotation playbook in detail but there's no scheduled rotation or automation. Secrets that need rotation: Firebase Admin, RapidoReach (3 keys), ProxyCheck, Resend, PayPal, Tremendous, SESSION_SECRET.

**Fix:** Add a Vercel cron or GitHub Actions workflow that prompts for rotation on a quarterly basis.

---

#### P2 — ISSUE 6: Sentry Auth Token Over-Permissive

`SENTRY_AUTH_TOKEN` stored as an env var and passed to Sentry config (`sentry.server.config.ts`). If this token is compromised, attackers could inject events into Sentry, potentially masking security incidents by overwriting/suppressing legitimate alerts.

**Fix:** Scope the Sentry auth token to read-only + event write only, not project management.

---

#### P2 — ISSUE 7: Placeholder Phone Numbers in Monitoring

`better-uptime.yml` has hardcoded fake phone numbers (`+1xxx-xxx-xxxx`) in monitoring configs. Not a security issue per se, but signals incomplete production configuration that could cause missed alerts during an incident.

**Fix:** Replace with real on-call numbers.

---

#### P3 — ISSUE 8: CSRF Cookie `httpOnly: false`

`src/lib/csrf.ts` line 17 sets the CSRF cookie with `httpOnly: false`. This means JavaScript can read the CSRF token from the cookie, which opens a theoretical XSS-based CSRF theft path. In practice, `httpOnly: false` is required for the double-submit pattern to work (the client needs to read the cookie to send it in the header).

**Mitigation:** The XSS risk is managed by React's default escaping and CSP headers. Low priority but worth noting.

### 3D. Firestore Security Rules — Rating: A (Best-in-Class)

This is one of the strongest rule sets seen in a project of this complexity:

- User isolation enforced on ALL personal collections (`users`, `ledger_transactions`, `offer_clicks`, `offer_postbacks`, `cashout_requests`, `transactions`, `withdrawals`)
- Sensitive fields protected from client writes (`admin`, `walletBalanceCents`, `ledgerBalanceCoins`, `totalEarned`, `status`, `isFlagged`, `flaggedReason`) — the `affectedKeys().hasAny()` check is correct
- All write operations blocked on security-critical collections by clients only: `fraud_flags`, `admin_actions`, `admin_logs`, `admin/`, `blocked_ips` — all `allow read, write: if false`
- Events collection is append-only (users can create but not read/update/delete others' events)
- Offers collection globally readable, client-write blocked
- Ledger transactions immutable (clients can only read their own)
- Withdrawals and transactions: clients can read their own, all writes blocked (admin SDK only)

**Edge case:** The `users` allow update rule checks `affectedKeys().hasAny([...restricted])` which correctly rejects any update that touches sensitive fields. If a user update includes both allowed and restricted fields in the same request, it will be entirely rejected (fail-closed), which is the right behavior.
